# Android APK 落地方案：先做安全的 Windows 伴侣，再评估独立版

> 本文是实施建议，不是已经完成的 Android 产品。本次仅新增此方案文件，不实现 APK、不修改现有服务、不开放端口。工期均为粗略工程估算，不构成交付承诺。

## 一、建议与边界

**推荐第一阶段做 Kotlin 原生外壳 + WebView + 配对 HTTPS 网关的 Windows 伴侣 APK。** 手机负责交互、任务查看和文件接收，Windows 电脑继续负责平台访问、转换与可选 AI 计算。电脑必须开机、服务运行且手机能访问其受控局域网入口；这不是“脱离电脑运行”的独立版。

第二阶段只挑选可移植的功能做 Android 本地实现，默认 Kotlin，必要时验证 Chaquopy 复用少量纯 Python 逻辑。第三阶段把手机端 AI 作为独立研究项目，先测模型、内存、耗时、温升和许可证，再决定是否产品化。

不推荐以下捷径：

- 仅给网页套壳就宣称全部功能已经移植。
- 把 Flask 改为监听 `0.0.0.0`，然后让手机直接访问所有现有接口。
- 把 Windows EXE、Node、Python 和 AI 安装包原样装进 APK。
- 为让咪咕／HiFiTi 在手机上可用而直接删除本机访问、owner 或 CSRF 校验。
- 在未测试之前承诺所有平台、账号权益、音质、机型或手机端 AI 均可用。

## 二、现有架构及移植影响

以下为基于相关源码的最小范围核对，不是完整安全审计；未读取账号文件、Cookie 或其他凭据。

| 现状 | Android 影响 |
| --- | --- |
| `startup.py` 默认使用 Flask `127.0.0.1:8899`；启动逻辑可能选择其他可用端口 | 手机的 `127.0.0.1` 是手机自身，不是电脑。连接信息应来自当前电脑实例，而不是写死端口 |
| `app.py` 提供页面和 API，`static/index.html` 使用相对地址访问接口 | 原页面依赖同源；远程访问须同时设计 UI、API、Cookie、文件与流式传输的来源关系 |
| `netease_api.py` 调用 Node 桥接；`qq_api.py` 的 QQ 歌单调用 Node 桥接 | Python 能运行不代表桥接功能能运行；Android 独立版需替换或重新适配 Node 依赖 |
| `ffmpeg_api.py` 寻找 Windows `ffmpeg.exe` | Android 必须使用适配 ABI 的原生库／工具或系统媒体能力，不能执行该 EXE |
| `ncm_api.py` 使用用户提供的 `ncm转mp3.exe` | Android 需重新寻找许可明确、可验证的实现；转换结果可能是原始 MP3 或 FLAC，并非必然 MP3 |
| `vip_api.py` 通过 Node 包装 Unlock Music WASM 处理 mflac 等文件 | WASM 不等于可直接搬运。运行时、文件接口、内存占用与格式覆盖都需另测 |
| `vocal_api.py` 对接可选 Windows AI `start.exe`，HTTP 地址为 `127.0.0.1:9999`；安装包约 749 MB | 第一阶段仅复用电脑端 AI；不能据此推导出可用的 Android 推理引擎或 APK 体积 |
| 网易云相关入口有来源限制；咪咕登录、HiFiTi 有 loopback、owner 和 CSRF 校验 | 原有本机信任边界不能自动扩展到局域网；网关必须明确外部设备身份和内部会话映射 |
| 存在目录配置、文件转换、上传、清空文件夹、打开电脑目录和 AI 安装等接口 | 这是具备电脑操作能力的应用，不是只读网页。开放前必须做全应用认证、权限、路径和上传安全审计 |

参考入口：`app.py`、`startup.py`、`static/index.html`、`netease_api.py`、`qq_api.py`、`vip_api.py`、`ncm_api.py`、`ffmpeg_api.py`、`migu_login.py`、`hifiti_api.py`、`vocal_api.py`。这些事实不能替代逐路由、逐文件操作的审计结论。

## 三、功能可行性矩阵

“可复用”仅指架构可行，不保证第三方服务持续有效；账号权益、地区、风控、接口变化及网络条件仍然生效。

| 功能 | 第一阶段：Windows 伴侣 | 第二阶段：手机独立运行 | 首版建议 |
| --- | --- | --- | --- |
| QQ／网易云搜索、歌词 | 电脑执行，手机展示；需按来源验证 | 选择一种来源优先重写网络层，验证签名、依赖和合规 | 纳入经过回归的来源 |
| QQ 歌单（现版网易云不支持歌单） | 可复用电脑 QQ Node 桥接 | 替换相关签名与协议；网易云歌单需另行实现 | 先只读导入，限制规模 |
| 按权益下载音频 | 电脑创建任务，手机接收授权结果 | 需验证授权协议、文件校验、错误分类和后台恢复 | 纳入有限来源与格式 |
| 全民 K 歌链接处理 | 可复用电脑实现 | 评估网络与解析逻辑的可移植性 | 不作为首版阻塞项 |
| 咪咕登录／搜索／按授权下载／歌词 | 现有能力有条件复用；登录与会话边界需专门适配 | 登录协议、二维码、授权事务和生命周期均需重做验证 | 默认不纳入 MVP，验证后增量开放 |
| HiFiTi 浏览／登录／注册 | 需保持 owner 隔离、来源限制和内容净化 | 独立网络会话、网页内容安全与平台变更成本高 | MVP 排除账号写操作 |
| 电脑文件列表、下载到手机 | 可行，须绑定设备权限与文件 ID | 本地文件管理由 SAF／MediaStore 替代 | 纳入授权目录内文件 |
| FFmpeg 格式转换 | 由电脑执行，返回任务结果 | Android 原生媒体方案或裁剪 FFmpeg，另做许可与性能验证 | 首版只支持电脑端选定格式 |
| NCM 转换 | 复用电脑已有工具，明确实际输出格式 | Windows EXE 不可用；需独立实现和测试样本 | 不承诺手机本地支持 |
| mflac／mgg／qmc 转换 | 复用电脑 Node + WASM，限合法持有的文件 | 测试 WASM 运行时或可移植替代，不能保证所有变体 | MVP 不开放任意电脑路径 |
| AI 人声／伴奏分离 | 可选电脑能力；安装、内存与耗时仍由电脑承担 | 另立项选择移动模型和推理后端 | 不作为 MVP 验收必需项 |
| 打开电脑目录、全量清空、修改系统路径、安装组件 | 技术上能代理，但风险高 | 与 Android 语义不同，不应照搬 | MVP 禁用 |

## 四、第一阶段：范围明确的伴侣 MVP

### 4.1 用户流程

1. **电脑准备**：启动 Windows 应用，进入“手机连接”，主动开启配对网关；首次明确提示局域网暴露范围和可授权能力。默认关闭，退出或撤销后不可继续使用。
2. **扫码配对**：APK 扫描电脑屏幕二维码，显示电脑标识与校验信息；电脑端确认此次设备与权限。二维码携带短期、一次性配对材料及证书校验信息，不包含平台 Cookie、密码或长期访问令牌。
3. **日常使用**：手机在同一受信网络连接已配对电脑，搜索、查看歌词、提交下载任务。界面始终区分“保存到电脑”和“下载到手机”，不误导用户认为文件已经落在手机。
4. **接收文件**：电脑完成任务后，手机以受认证请求取回结果，经原生下载流程写入 MediaStore 或用户通过 SAF 选择的位置。显示进度、实际格式、失败原因及可重试状态。
5. **断开恢复**：网络切换、电脑休眠或服务重启时显示离线；重连后按任务 ID 查询状态，不盲目重建下载任务。电脑计算可继续，手机接收需按条件恢复。
6. **取消与撤销**：支持取消本人任务、退出登录和电脑端撤销设备；明确区分应用配对授权与音乐平台账号授权。撤销后已有会话和文件接收权限应失效。

### 4.2 MVP 纳入内容

- 单台电脑、单个家庭／个人所有者模型；可记录多个配对设备，但不宣称多租户隔离。
- Kotlin 连接与配对页、受控 WebView、手机窄屏适配。
- 经回归的一至两个音乐来源：搜索、歌词、有限歌单、授权下载。
- 任务 ID、状态查询、重连恢复、限定输出文件列表、下载到手机。
- 最小设备权限、撤销、日志脱敏和发布签名流程。

### 4.3 MVP 明确排除

- 不需要电脑的全功能独立版；公网访问、端口转发、云中继、跨家庭远程管理。
- 任意电脑目录浏览、修改监控路径、打开资源管理器、一键清空文件和远程安装 AI。
- 未经专门设计的远程账号管理、Cookie 导入导出及 HiFiTi 注册。
- 通用上传与手机本地批量解密；无限大小文件或无限并发任务。
- 手机本地 AI、后台永久保活、所有 Android 厂商机型完全一致的运行体验。
- 绕过付费、DRM、下载授权或平台限制。

## 五、第一阶段技术设计

### 5.1 分层与网络

```text
Android APK
  Kotlin：配对、证书信任、凭据保管、文件接收、生命周期
  WebView：受控同源 UI
        |
        | HTTPS；配对设备认证；能力授权
        v
Windows 手机网关（新增、默认关闭、局域网指定接口）
  静态 UI + 白名单 API + 会话/权限 + 限流 + 任务/文件 ID
        |
        | 受控内部适配层；固定目标；无通用 URL 转发
        v
现有 Flask（继续 loopback，默认 8899）
  Python / Node / Windows FFmpeg / NCM 工具
        |
        +-- 可选 AI HTTP 127.0.0.1:9999（不对手机直接开放）
```

网关不是“所有端点反向代理器”。它应提供窄接口门面，只映射明确允许的业务操作；不能接收客户端指定的上游 URL、文件系统路径或内部端口。Windows 防火墙规则应限定应用、私有网络及必要来源；不用路由器端口映射，不把 8899、9999 暴露给局域网。

UI 与手机 API 在网关上保持同源，避免依赖跨域放开。用服务身份识别和内部受信交接获取当前 Flask 实例地址，不信任任意监听在某个端口的进程。网关关闭后 Windows 原本的本机使用方式继续工作。

### 5.2 配对与 HTTPS

- 原生配对流程先验证电脑身份，再交换设备凭据；一次性票据短期失效、限次尝试、禁止重放，并由电脑确认。局域网本身不视为可信。
- HTTPS 必须具备可验证的信任链或经过带外确认的证书／公钥绑定。局域网自签名证书需要完整信任引导，不是勾选“忽略证书错误”。
- 先做证书方案验证：普通 WebView 和原生网络层须遵守一致的信任策略，覆盖页面、子资源、API、重定向及文件下载。可以选择可验证证书的固定主机名；如采用动态证书绑定与原生受控网络传输，必须证明整个 WebView 请求路径均被正确保护，不能只给下载客户端做 pinning。
- 禁止通过 `onReceivedSslError(...).proceed()`、信任所有证书或关闭主机名校验解决兼容性。无法建立安全 HTTPS 时停止连接，而非降级明文。
- 设备长期凭据由 Android Keystore 支撑的加密存储保护，短期会话可轮换、可撤销；不放入 URL、网页 localStorage、剪贴板或日志。需要 Cookie 时使用受限、短期、`Secure`、`HttpOnly`、适当 `SameSite` 的网关会话。
- 更换电脑证书、重装电脑服务、撤销后重连应重新确认；实现证书轮换和丢失手机后的撤销流程。

### 5.3 原有 owner、CSRF 与平台会话

咪咕／HiFiTi 的 loopback 校验不是网关认证的替代物。代理请求来自本机，也不代表请求已被授权。

应明确区分三类身份：配对设备、网关会话／权限、平台账号／模块 owner。内部适配层为已授权设备维护独立模块会话，不能把所有手机请求映射到同一个通用 owner，也不能透传任意 Cookie、Host、Origin 或 `X-Forwarded-*`。

对外先执行认证、权限与 CSRF／来源验证；对内按审计后的固定协议建立请求与会话。涉及来源转换时，外部真实来源须先被严格验证，不能通过统一伪造为 localhost 来“通过安全检查”。现有 loopback 防线保持有效；如确需调整代码，应拆分出清晰的受信业务接口并回归验证，而不是移除保护。

首版建议在电脑上完成平台登录，手机仅使用所有者明确授权的能力，不导出平台凭据。部分现有模块可能使用全局账号状态，因此单个 owner Cookie 不足以证明多账号／多用户隔离；未完成数据隔离前不得宣传多用户模式。

### 5.4 WebView 与任务、文件

- WebView 仅加载已配对来源；阻止明文、混合内容、任意外域跳转及不受信页面调用原生能力。第三方链接交给外部浏览器，经确认打开。
- 禁止无必要的文件 URL 访问与宽泛 JavaScript bridge；如需桥接，只开放少量明确方法，逐次校验来源、参数及用户动作。网页不能请求任意电脑或手机路径。
- 长任务改为“提交任务 → 返回 ID → 查询／推送状态 → 获取结果”，实现幂等提交、并发限制、取消、超时和失败恢复。页面退出不应导致错误重复执行。
- 网关把可见文件映射为不可猜测且有权限检查的文件 ID；下载时再次认证和授权，支持必要的 Range／续传与完整性验证。不可把现有 `/files/` 整体无条件公开。
- 手机原生层处理受认证的文件接收；系统下载组件不一定继承 WebView Cookie 或证书策略，不能假设点击下载就安全可用。下载完成后再原子提交最终文件，避免半文件冒充成功。

## 六、开放前的全应用安全门槛

以下是上线前必做事项，不代表已经确认每项都存在可利用漏洞。

1. **完整路由清单**：覆盖 HTML、静态资源、所有 API、文件、上传、健康检查、任务状态和错误页。敏感接口默认拒绝，不能只保护登录页或部分音乐来源。
2. **认证与能力权限**：区分查询、提交任务、读取结果、删除文件、配置路径、上传、安装组件与管理设备。电脑管理类操作首版不对外；设备不能读取或取消未授权任务。
3. **路径边界**：审计转换和 AI 等由 `name`／`path` 拼接路径的入口。优先使用服务端 ID；检查绝对路径、`..`、编码变体、UNC／盘符、符号链接及 Windows junction，解析后验证真实路径位于允许根目录。`send_from_directory` 的保护不能替代其他路径入口的审计。
4. **上传边界**：启用前定义文件大小、总配额、数量、扩展名、媒体实际类型、解码时长与计算资源上限。随机临时名、独立隔离目录、拒绝覆盖、失败清理；不信任客户端文件名和 MIME，不将输入交给 shell。MVP 禁用上传并不免除全应用审计。
5. **外部请求与子进程**：防 SSRF、重定向绕过、私网目标访问和命令注入；固定可执行程序、参数白名单、超时、输出上限与最小权限。网关不得成为访问电脑 localhost 服务的通用跳板。
6. **来源与会话**：严格 Host／Origin 验证、防 DNS rebinding；Cookie 操作保持 CSRF 防护，不启用任意 CORS。拒绝不受信转发头，撤销及时生效，限制配对和账号尝试频率。
7. **内容与信息泄露**：净化外部歌词、论坛文本和链接，防 XSS 及原生桥滥用。对外健康状态不泄露本机目录；错误不返回堆栈、平台响应或凭据。日志仅记录必要事件与脱敏标识。
8. **传输与资源隔离**：限定流量、任务并发、磁盘空间和 AI 资源；权限撤销后禁止后续读取。明确已经下载到手机的文件无法被远程收回。

交付门槛：完成端点审计及修复、未配对访问测试、越权与撤销测试，才允许在受控局域网试用。

## 七、第二阶段：选择性独立版

### 7.1 建议的最小独立目标

先选一个已验证来源，完成搜索、歌词、依法授权的下载、手机本地列表和导出；再按收益决定是否加入歌单、转换和更多平台。不得把“所有 Windows 功能全搬过去”作为一次性目标。

- **Kotlin 优先**：网络、文件、任务与系统交互采用原生实现；协议解析尽量独立，便于测试和跟进平台变化。
- **Chaquopy 可选**：仅用于已证明能带来收益的 Python 逻辑；检查 Python 版本、ABI、依赖 wheel 和包体。它不会自动提供 Windows 子进程、Node、FFmpeg 或 AI 引擎，也不能解决后台生命周期。
- **Node 替代**：逐项梳理网易云及 QQ 歌单的签名／加密／协议依赖，优先移植必要算法和请求层。若评估嵌入 Android Node，需单独验证维护性、ABI、安全更新与生命周期；不默认把它作为标准路线。
- **FFmpeg 替代**：先确认系统媒体能力能否覆盖目标格式；不足时评估仍在维护、许可证清晰的 Android FFmpeg 构建，裁剪不需要的编解码器并测大文件、耗电和崩溃恢复。不得直接使用 Windows EXE。
- **NCM／mflac**：以合法样本和许可为前提，分别验证格式覆盖、输入输出一致性、峰值内存和失败恢复。WASM 可考虑专用隔离运行环境，但不默认复用展示不受信内容的 WebView。旧格式成功不代表新格式都可用。

### 7.2 Android 系统适配

- **SAF**：通过系统选择器获取输入文件／目录 URI，按需持久化授权；处理授权被撤销、文档提供器离线与不可 seek 的输入流。URI 不是可以直接传给桌面库的路径。
- **MediaStore**：把公共音频写入适当集合，处理待发布状态、重名、空间不足及删除授权。避免申请全盘文件访问权限；读取用户媒体时按实际系统版本申请最小权限。
- **Keystore**：保护平台令牌和设备凭据，明确备份／恢复后失效策略，不把密钥硬编码进 APK。
- **WorkManager 与生命周期**：适合可延迟、可恢复的后台工作；不保证任务即时执行或永不停止。长时间用户可见传输／计算依目标 Android 版本采用适当的前台工作机制、通知和权限，并遵守后台启动限制。
- 使用持久化任务记录处理 Activity 重建、进程被杀、Doze、网络切换、重启与厂商省电。取消要能释放网络、文件句柄和原生计算资源。

### 7.3 二维码、深链与同机登录

手机显示的平台登录二维码往往需要同一平台的手机 App 扫码；只有一部手机时，不能要求用户“用本机摄像头扫描本机屏幕”。伴侣版可优先在电脑显示二维码由手机扫描；独立版需验证平台是否提供官方深链、授权回调或允许的相册识别方式。没有已验证方案时，应明确需要第二块屏幕或暂不支持该登录方式，不承诺自动完成。

深链只接受预期 scheme／host／path，授权回调验证 state、时效与防重放；优先使用可验证的 App Links，并避免把令牌写入可被其他应用截获的链接。外部平台 App 是否安装、是否支持回调、是否触发风控，都须实机验证。

## 八、第三阶段：手机端 AI 单独立项

现有约 749 MB 是 Windows AI 组件下载量，不是 Android 模型大小、运行内存或安装空间指标。`start.exe` 与其 Python／推理依赖不能直接复用。

先做测量型原型：选择许可允许的模型与移动推理后端，例如经兼容性验证的 ONNX Runtime Mobile、LiteRT 或其他合适方案；测量目标 arm64 真机上的音质、分块边界、速度、峰值内存、磁盘、耗电、温升、后台中断与恢复。需要分别验证 2 轨和更多轨道，不推断桌面模型一定有可用的移动版本。

仅在结果可接受时讨论量化、模型按需下载、完整性校验、资源限制和产品体验。无可接受结果则继续使用电脑计算。**不承诺实时、离线全模型、低端机可用或与电脑输出完全一致。**

## 十、APK 签名与发布

- 推荐 Kotlin + Android Studio／Gradle，先做内部测试的 release APK。伴侣版不嵌入大型本地计算依赖，ABI 负担较小；涉及原生组件的独立版优先验证 **arm64-v8a**，按需求另做其他 ABI，不默认为所有架构打一个大包。
- APK 用于用户侧安装；如以后上应用商店，再按渠道要求产出 AAB、适配目标 SDK、隐私说明及内容／媒体政策，不承诺上架审核一定通过。
- 固定 applicationId，递增 versionCode，定义网关与 APK 的兼容协议版本。电脑与 APK 版本不匹配时提供明确升级指引。
- 生成并由项目所有者保管正式签名密钥，调试密钥不能作为正式发布密钥。**私有签名密钥、keystore 文件、密码、平台凭据和配对秘密必须排除在源码仓库、APK、文档、日志及普通构建产物之外。** 使用受控离线保管／密钥管理和加密备份，限制 CI 权限；本文不要求创建或提交任何密钥。
- 发布前运行签名验证、依赖与许可证检查、包体秘密扫描，并提供 APK 校验值、版本说明及兼容范围。相同渠道升级须保持正确签名关系，提前设计密钥丢失／轮换的恢复路径。
- 整理 Python、Node 包、WASM、FFmpeg 和 AI 的许可证／再分发要求。现有工具“能运行”不代表可合法捆绑到 Android 发行版。

## 十一、工作量与推进顺序

单位为**工程师周（1 名工程师投入 1 周）**，含开发与基础测试的粗略区间；不是自然周排期，也不是固定报价。假设开发者熟悉现有 Python 与 Android，且平台协议没有重大变化。正式估算应在第一轮审计与原型后更新。

| 工作包 | 粗估 | 主要不确定性 |
| --- | --- | --- |
| 第一阶段 A：全路由审计、范围冻结、配对／HTTPS／owner 适配原型 | 2–4 工程师周 | 既有路径与权限问题、WebView 证书路径、全局平台账号状态 |

| 第二阶段增量：本地转换／Node 或 WASM 替代验证与产品化 | 另约 4–10 工程师周起 | 必须先做技术验证；失败时可能不交付该能力 |
| 第三阶段：手机 AI 可行性原型与测量 | 约 3–6 工程师周 | 只交测量结论；可能得出不适合产品化 |

多人并行不代表自然周按人数直接相除；业务审计、证书原型、接口冻结与联调有先后依赖。设备采购、账号／平台审核、商店审核、重大第三方修复和持续维护未计入。AI 产品化在测量之前不估固定交付周期。

建议按以下停止／继续条件推进：

1. **先审计和原型**：证明外部设备认证、完整 HTTPS 信任链、模块 owner 边界和安全文件访问成立；不成立就不开放局域网入口。
2. **冻结伴侣 MVP**：只验收明确列出的来源、操作与设备范围；交付签名 APK 和匹配的 Windows 网关版本。
3. **小范围试用**：收集脱敏的网络、断点恢复和系统兼容问题，不收集用户平台秘密。
4. **再选择独立功能**：按真实需求和迁移成本逐项立项；AI 独立评估，不拖累伴侣版。

## 十二、最终结论与诚实限制

当前架构最务实的第一步是**安全的 Windows 伴侣 APK**，不是把整个桌面程序移入手机。它能较早复用现有业务能力，但代价是电脑必须在线，且新增网关会显著扩大安全责任；全应用审计不能省略。

真正独立的 Android 版需要重新处理 Node 桥接、Windows EXE、媒体库、文件授权、登录方式与后台任务。平台授权与风控不受本项目控制，移动网络和系统省电也会影响体验。对于尚未验证的格式、登录、平台或 AI，只能给出试验路径，不能作功能承诺。

**本次交付仅为本文方案；未生成 APK、未实现网关、未调整监听地址，也未修改其他文件。**
